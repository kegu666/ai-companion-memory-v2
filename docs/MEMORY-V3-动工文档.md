# Memory V3 动工文档：记忆分类、强化与衰退

状态：设计稿，先定规则，再动代码。

这次改造解决一个问题：聊天原文可以全部保存，但模型每次不应该把所有历史都当成同样重要的记忆。
我们需要让近期对话、长期事实、临时事件和冷记忆在保存、压缩和检索时承担不同职责。

## 一、先把几个概念分开

目前讨论的四个词不在同一层：

| 名称 | 实际含义 | 是否属于记忆类型 |
| --- | --- | --- |
| 近期对话 | 当前聊天的工作上下文 | 否 |
| 长期事实 | 可以长期使用的人物资料或稳定事实 | 是 |
| 临时事件 | 某次发生的事情、短期计划 | 是 |
| 冷记忆 | 不主动塞进上下文，需要相关问题唤醒 | 否，是检索状态 |

因此 V3 使用两个维度：

1. `kind` 描述内容是什么：事件、事实、偏好、计划、关系、话题。
2. `temperature` 描述当前是否应该主动想起：`hot`、`warm`、`cold`、`expired`。

“近期对话”由系统自动保留最近若干条，不让整理模型把每条普通聊天都登记成长期记忆。

## 二、记忆记录的目标结构

在现有 `memories` 表上增加这些字段。完整原文 `turns` 表继续保存，不因衰退删除：

~~~text
kind             内容类型
temperature      hot / warm / cold / expired
importance       0.0 - 1.0，重要程度
confidence       0.0 - 1.0，来源和判断可信度
first_seen_at    第一次出现时间
last_reinforced  最近被提到、确认或成功使用的时间
recall_count     被检索并采用的次数
expires_at       计划或临时事件的明确过期时间，可为空
decay_half_life  衰退半衰期，单位为天
last_accessed    最近一次被检索的时间
metadata         JSON，保存重复提及、情绪、日期等扩展信息
~~~

这些字段用于调整检索优先级，不等于直接删除聊天记录。

## 三、第一版标签规则

| 内容 | `kind` | 初始温度 | 初始衰退建议 | 示例 |
| --- | --- | --- | --- | --- |
| 某天发生的事情 | `event` | `hot` | 7～30 天 | 昨晚吃了火锅 |
| 有明确时间的安排 | `plan` | `warm` | 由 `expires_at` 控制 | 下周去看电影 |
| 长期兴趣或习惯 | `preference` | `warm` | 180 天以上 | 不喜欢香菜 |
| 人物资料和稳定事实 | `fact` | `warm` | 先不自动过期，冲突时更新 | 现在住深圳 |
| 人际关系和重要经历 | `relationship` | `warm` 或 `cold` | 30～365 天 | 和某人关系紧张 |
| 正在讨论的话题 | `topic` | `hot` | 14～60 天 | 最近在考虑换工作 |

这些天数只是第一组可调参数，不代表真实的人类记忆规律。
重要程度高、被重复提及、用户明确说“记住”的内容，应得到强化；普通事件不能因为刚发生就永久保留高权重。

## 四、整理模型负责什么

整理模型继续负责摘要和候选记忆提取，但输出需要增加标签：

~~~json
{
  "kind": "preference",
  "temperature": "warm",
  "importance": 0.8,
  "confidence": 0.9,
  "expiresAt": null,
  "content": "用户喜欢无糖咖啡",
  "sourceIds": [123],
  "quote": "我喜欢喝无糖咖啡",
  "slot": "drink"
}
~~~

模型可以提出标签，但程序不能直接相信标签：

- `sourceIds` 必须存在，并且属于同一会话和同一用户。
- `quote` 必须逐字出现在用户原话中，不能引用助手自己生成的内容。
- 事实和偏好默认先进入 `candidate`，确认后才参与长期检索。
- `expiresAt` 必须是可解析的未来时间；无法确认时留空。
- `importance` 和 `confidence` 超出范围时截断或拒绝。
- 模型没有权限直接把旧事实删除，替代关系由程序建立。

摘要仍然只是工作上下文，不是已经确认的事实。

## 五、衰退不是删除

检索分数改为多因素组合：

~~~text
最终分数 =
  语义相关度
  + 关键词相关度
  + 重要程度
  + 可信度
  + 重复提及加成
  + 用户主动询问加成
  - 时间衰退
~~~

一个可实现的衰退函数是：

~~~text
decay(ageDays) = 0.5 ^ (ageDays / decayHalfLife)
~~~

时间衰退只降低默认检索权重：

- 用户直接问到相关内容时，冷记忆仍然可以被唤醒。
- 用户再次提到同一事实时，更新 `last_reinforced` 并提高权重。
- 用户说“记住这个”时，提高 `importance`，但仍保留来源。
- 新事实与旧事实冲突时，旧事实进入 `superseded`，不靠衰退解决冲突。
- 过期计划降为 `expired`，原文和来源仍可查询。

这样可以出现“很久以前的重要事情仍然记得”和“刚发生的小事很快淡掉”这两种情况。

## 六、上下文怎么组装

每次回复按以下顺序给模型：

1. 角色卡和当前处境。
2. 最近若干条原始对话，保证当前聊天连贯。
3. 当前会话摘要，标记为可能陈旧的整理结果。
4. 按当前问题检索到的已确认记忆。
5. 必要时加入冷记忆或过期事件的少量来源摘录。

近期对话不走长期记忆衰退；它有独立的条数和字符预算。
长期记忆也不全部注入，只取相关结果。

## 七、和现有 Memory V2 的迁移关系

V2 的以下行为保持不变：

- 完整 `turns` 原文保留。
- `candidate` 不参与长期检索。
- 私聊、群聊和不同群之间按 scope 隔离。
- 记忆确认后可以按 `slot` 替代旧事实。
- embedding 失败时继续使用关键词检索。

迁移时：

1. 已确认的 `fact`、`trait`、`preference` 默认导入为 `warm`。
2. `topic`、`pending` 默认导入为 `hot` 或 `warm`，等待下一次整理重新判断。
3. 没有来源的旧数据保留，但 `confidence` 降低，不能伪装成模型核验过的事实。
4. 所有新字段设置默认值，旧数据库可以原地升级，不能清空重建。
5. 先只改变检索排序，不做自动物理删除，方便回滚和比较效果。

数据库 schema 从 V2 升到 V3 时，需要记录迁移版本并提供失败回滚。

## 八、分阶段动工顺序

### 第一步：数据结构和标签校验

- 增加字段和 schema 迁移。
- 扩展整理模型 JSON 协议。
- 增加默认值、范围检查和来源校验。
- 旧 JSON 和 V2 数据可继续读取。

### 第二步：只改检索，不改删除

- 为不同 `kind` 设置衰退参数。
- 加入重要度、可信度和重复提及加成。
- 记录检索次数，但不把“被检索过”直接当成事实确认。
- 保留旧排序作为开关，便于 A/B 对比。

### 第三步：做强化和过期处理

- 重复提及更新 `last_reinforced`。
- 计划根据日期进入 `expired`。
- 明确更正建立 `superseded` 链。
- 管理 CLI 能查看标签、来源、衰退分数和更新时间。

### 第四步：用真实聊天样本评估

准备几类回归样本：

- 近期小事是否会自然淡出。
- 长期偏好是否仍能被找回。
- 用户更正后旧事实是否不再主导回答。
- 冷记忆被直接问及时能否召回。
- 私聊记忆是否仍然不会进入群聊。

没有这组样本前，不调整参数去追求“看起来像人”，也不宣称已经解决记忆错乱。

## 九、明确不做的事情

- 不按时间自动删除全部原始聊天。
- 不让模型单独决定永久记忆或彻底遗忘。
- 不把“最近出现”当作“最重要”。
- 不把摘要当作事实来源。
- 不在没有评估数据时承诺人类级记忆。
- 不在这一阶段引入独立向量数据库或复杂 ANN 服务。

第一阶段的完成标准是：标签可追溯、衰退只影响检索、原文可恢复、旧数据库可迁移、关键回归样本通过。
